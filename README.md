# Trello Cucumber BDD Automation

A portfolio project built to demonstrate Behavior-Driven Development (BDD) test automation using Playwright, Cucumber.js, and JavaScript.

Trello serves as the application under test. The framework combines API-driven test setup and cleanup with UI-driven workflow validation to create a realistic end-to-end automation solution.

This repository showcases BDD and automation-framework development skills. It is intended for learning and portfolio purposes rather than as a reusable Trello management utility.

---

## Project Objective

The framework demonstrates how a business workflow can be expressed through readable Gherkin scenarios and implemented using modern test-automation practices:

* Cucumber feature files
* Gherkin (Given, When, and Then)
* Cucumber DataTables
* Cucumber lifecycle hooks
* Playwright Page Object Model
* Trello REST API integration
* Stored browser authentication
* Failure screenshot capture
* Cucumber HTML reporting

---

## Automated Business Workflow

The framework automates the following workflow:

1. Create a disposable Trello board through the API
2. Retrieve and validate the required workflow lists:
   * **To Do**
   * **Doing**
   * **Done**
3. Open the board through the Trello UI using saved authentication
4. Create project cards in the **To Do** list
5. Validate all cards in **To Do**
6. Move all cards from **To Do** to **Doing**
7. Validate all cards in **Doing**
8. Move all cards from **Doing** to **Done**
9. Validate all cards in **Done**
10. Delete the disposable board through the API

> A uniquely named board is generated during every execution to prevent conflicts with existing test data.

---

## Workflow Design

The automation is intentionally implemented as a single business workflow split across three scenarios.

### Shared State

The scenarios share:

* One disposable Trello board
* One authenticated browser session
* One browser page
* The cards created during execution
* Application state generated by the preceding scenarios

The scenarios execute sequentially because each scenario depends on the state produced by the previous scenario.

Parallel execution and individual scenario retries are intentionally avoided because a retry or parallel run could begin with cards located in an unexpected workflow stage.

---

## API and UI Integration

### Trello REST API

The API layer is used for:

* Creating disposable test boards
* Retrieving board lists
* Validating required workflow lists
* Cleaning up test data after execution

### Playwright UI Automation

The UI layer is used for:

* Opening Trello with saved authentication
* Creating project cards
* Moving cards through workflow stages
* Validating the user-visible state

Using the API for setup and cleanup keeps the UI automation focused on validating the actual user workflow.

## Installation

### Clone the Repository

```bash
git clone https://github.com/arunbalaji123/trello-playwright-cucumber-bdd.git
```

### Navigate to the Project

```bash
cd trello-playwright-cucumber-bdd
```

### Install Dependencies

```bash
npm install
```

### Install Playwright Chromium

```bash
npx playwright install chromium
```

---

## Environment Configuration

Create a `.env` file in the project root:

```env
TRELLO_API_KEY=your_trello_api_key
TRELLO_TOKEN=your_trello_token
```

> **Note:** The `.env` file contains sensitive credentials and must never be committed to source control.

---

## Trello Authentication

The UI workflow uses a Playwright storage-state file:

```text
playwright/.auth/trello.json
```

This file is generated after completing a one-time Trello login and saving the authenticated browser context.

> **Note:** The storage-state file contains active browser-session data and must not be committed to GitHub.

## Running the Tests

Execute the complete BDD workflow:

```bash
npm run test_Bdd
```

The equivalent Cucumber command is:

```bash
npx cucumber-js --tags "@UI" --format progress --format "html:reports/cucumber_report.html" --exit
```

---

## Cucumber HTML Report

After execution, an HTML report is generated at:

```text
reports/cucumber_report.html
```

Open the report on Windows:

```powershell
Start-Process ".\reports\cucumber_report.html"
```

### Report Contents

* Feature and scenario results
* Gherkin step execution
* Cucumber DataTable values
* Execution duration
* Pass or fail status
* Error details
* Embedded failure screenshots

---

## Failure Evidence

When a test step fails, the framework automatically:

* Captures a full-page screenshot
* Stores the screenshot in the `screenshots/` directory
* Attaches the screenshot to the Cucumber HTML report

This provides clear evidence of the application state at the exact point of failure.
